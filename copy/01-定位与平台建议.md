# 手书 Tekaku：定位与平台建议

制定日期：2026-10-30（日本时间）。目标用户：学生与程序员兼顾。

## 推荐的产品定位

**给学生和程序员的轻量本地 Markdown 编辑器。**

一句话：**学习笔记、技术文档，在同一页边写边呈现。**

主张顺序：输入即呈现 → 多文件标签 → 本地文件 → 常用内容块 → 轻量下载包。灰蓝主题用来形成视觉记忆。

学生侧重点：课程笔记、读书摘录、待办清单、课题记录。程序员侧重点：项目 README、开发笔记、代码片段、技术文档。面向愿意用 Markdown 的学生，不把普通办公用户都当作目标人群。

不要定位为云端知识库、团队协作平台或全能办公套件。手机与电脑分别使用各自本地文件，目前不提供自动同步。宣传不暗示已支持 iPhone、macOS 或 Linux。

## 平台优先级

| 优先级 | 平台 | 为什么匹配 | 首发内容 | 看什么反馈 |
|---|---|---|---|---|
| 第一梯队 | 小红书 | 学生笔记、学习工具、桌面软件与简洁界面的图文表达匹配 | 6 张竖版图，配一个实际笔记场景；品牌版与学生场景标题分别测试 | 有效评论、收藏、主页/项目说明访问，不只看点赞 |
| 第一梯队 | B站 | 需要看到“边写边呈现”的真实过程，录屏比静态卖点更能解释产品 | 60–90 秒真实编辑录屏，横版封面使用 07；先写笔记，再放代码 | 完播、用户提出的具体问题、主动试用反馈 |
| 第一梯队 | V2EX「分享创造」等合适板块 | 开发者与个人软件作者更容易讨论具体需求、实现与缺点 | 作者身份介绍，附源码、支持范围、已知问题，邀请小范围测试 | 成功打开/保存、故障复现、愿意继续使用的场景 |
| 第二梯队 | 掘金 | 程序员文档与实现文章匹配，可同时介绍产品和技术取舍 | Go + 系统 WebView2 的桌面方案、单编辑器多 Tab、文件保存保护 | 有实质的问题与开发者试用，不把技术文章写成纯广告 |
| 第二梯队 | 少数派 | 写作工具与个人效率流程契合，适合完整体验文章 | 从课程笔记或项目文档出发，展示真实工作流与边界 | 深度反馈与持续使用意愿；能否被编辑推荐不作承诺 |
| 补充 | 酷安 | Android 工具用户适合反馈文件打开、编辑、分享入口等移动场景 | 单独介绍 Android 本地 Markdown 编辑，使用图 05 | 手机实际文件授权、保存成功、系统 WebView 兼容性 |
| 承接与信任 | GitHub | 让用户查看源码、版本与已知问题，承接各平台带来的兴趣 | 完整 README、版本说明、真实截图与问题反馈入口 | 可复现的 Issue 和功能需求；Star 不能等同活跃用户 |

建议实际顺序：**小红书与 B站展示体验，V2EX 招募早期反馈，GitHub 承接说明；随后做掘金与少数派的长内容。** Android 版在酷安单独讲，不强行用 Windows 的卖点套用。

Product Hunt、Hacker News 和大规模搜索广告暂放后面。当前更需要把 Windows 打开体验、安装信任和反馈闭环做好，再准备英文介绍与一次完整发布。以上是受众与形式匹配判断，不是实时流量排名或效果保证。

## 自然发布与付费推广怎么安排

当前优先自然发布与小范围公开测试。此前 Windows 下载存在未查明的杀毒拦截报告，跨进程文件转交也缺少 Windows 实机验证；付费扩大下载量会同时放大这些转化障碍。

进入付费测试之前，先取得具体检测名称并完成复核、积累 Windows 实机打开/保存/升级反馈，并把下载页的依赖与已知问题说明清楚。广告审核也不等于安全背书。

满足这些条件后，再考虑用平台官方推广工具小额测试一条已获得有效自然反馈的内容。先确定可承受的测试预算与止损线，不一开始多平台铺量。账号资格、推广入口、外链、商业推广与 AI 图像标识要求，以发布时的平台官方规则为准；这里不假定当前账号已具备投放资格。

## 第一周的低成本安排

| 时间 | 动作 | 产出 |
|---|---|---|
| 第 1 天 | 整理项目说明、当前版本、依赖与安全核查页；准备反馈模板 | 用户能在一个入口看懂支持什么、有什么已知问题 |
| 第 2 天 | 发小红书学生笔记切入版，图序 01→02→03→04→05→06 | 收集具体想用来写什么，而非只收“好看” |
| 第 3 天 | 发 B站真实编辑演示，使用 07 封面 | 展示输入、代码、多 Tab 和手动保存 |
| 第 4 天 | 在合适的开发者社区以作者身份分享并招募测试 | 收集 Windows 版本、操作步骤、成功或失败现象 |
| 第 5 天 | 针对最集中的问题更新 FAQ 或修复 | 记录实际变化，不使用虚构好评 |
| 第 6 天 | 发程序员文档切入版，主图可用 04 或 03 | 比较两类内容带来的有效反馈 |
| 第 7 天 | 汇总有价值的反馈与继续使用意愿 | 决定下周内容方向；不以曝光量单独判断效果 |

## 怎么判断有没有投对

按“看见内容 → 看懂场景 → 查看项目说明 → 成功打开/保存 → 愿意再次使用”逐步观察。链接点击不是下载，下载不是安装成功，Star 也不是持续使用。

当前应用不需要为宣传偷偷加入遥测。早期可用平台已有后台和用户主动反馈：询问从哪里看到、系统版本、是否打开成功、是否成功保存、三天后是否还在用。项目目前用 GitHub 分支原始文件提供下载，不能假定能读取公开的 Release 资产下载计数。

如果已有网站统计，可添加来源参数来区分内容；单独加参数并不会自动产生转化数据。没有网站统计时，先用人工、匿名、主动反馈即可。

## 可直接用的反馈问题

1. 你主要用它写课程笔记、技术文档，还是其他内容？
2. 你的系统版本是什么？是否顺利打开一个已有的 .md 文件？
3. 修改后能否保存并重新打开？遇到问题请写出步骤，不必上传私人文档。
4. 哪个操作最让你停下来？
5. 过几天你还会继续用它吗？为什么？
